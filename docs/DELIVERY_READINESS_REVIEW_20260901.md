# 因子库交付就绪评审报告

评审日期：2026-09-01

评审口径：站在客户付款验收视角，按“可合法使用、可完整接收、可直接部署、可稳定维护”的最严格标准审查当前仓库交付状态。

评审边界：
- 仅以仓库内可见代码、文档、配置、测试和可复现命令为准。
- 凡合同附件、法务文件、授权书、外部证据、客户手册、SLA 承诺未进入本仓库或未提供审阅，均按“当前不可验收/视同缺失”处理。

## 一、结论摘要

当前状态结论：**不具备对客户正式交付条件**。

主要原因不是单点缺陷，而是交付基础件同时缺失：
- 缺少客户可依赖的知识产权/授权链证明；
- 仓库自证当前仍处于“阶段 0 产品雏形/原型”状态；
- 交付范围、文档、测试、部署入口存在多处互相矛盾；
- 后端数据服务缺少客户级鉴权，存在持牌数据被匿名代理调用的合规风险；
- 仓库自身生命周期文档明确写明：当前完整实施 0 道 G2 验真、A 级因子 0、证书体系未落地。

因此，若以“客户支付 10 万定金后即可合法合规使用并顺利落地”为验收门槛，当前版本**不能签收**。

## 三、关键问题明细

### R1. 缺少客户可依赖的知识产权、授权链、非侵权证明材料

**判定**：高风险，阻断交付。

**证据**
- 仓库可见法律材料仅有 Apache 2.0 开源许可证，无法替代客户商用授权链：`README.md:265-267`，`LICENSE`
- 开源清理清单只是一份发布前检查表，不是权属证明、授权书或赔偿承诺：`OPEN_SOURCE_SANITIZATION_CHECKLIST.md`
- Alpha101 源文本明确写明 Appendix A 公式和代码版权归 WorldQuant LLC 保留：`docs/alphas 101.txt:614-616`
- 真实数据验证依赖私有 SmartData 报告，报告本身不在仓库内：`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:3-10`

**问题说明**
- 目前看不到任何以下客户必需材料：著作权归属说明、第三方数据授权边界、论文/公式/代码再分发许可、客户使用范围授权、侵权兜底声明、商用限制清单。
- 若客户依据当前仓库付款接收，无法确认其获得的是“开源仓库使用权”还是“商业因子产品使用权”。

**整改标准**
- 提供完整《交付法务包》：代码权属、第三方依赖授权清单、外部数据来源授权边界、客户商用许可范围、侵权争议响应条款。
- 对 Alpha101、SmartData、RQData、JoinQuant、Quant API 等外部来源逐项写明“可内部研究 / 可客户商用 / 不可再分发”的边界。

### R2. 仓库自证当前无可上架证书因子，不能对外宣称现货可交付

**判定**：高风险，阻断交付。

**证据**
- 生命周期文档明确写明：完整实施 0 道、部分 2 道、未实施 7 道；过完九道验真的因子数量为 0：`docs/FACTOR_LIFECYCLE.md:166-182`
- 文档明确要求“没有第一个证书之前，对外不得暗示有货”：`docs/FACTOR_LIFECYCLE.md:182`，`docs/FACTOR_LIFECYCLE.md:331`
- 证书 12 必填字段、人工批准、摘牌 SLA 等客户可见要件仍是规则要求，不是已交付事实：`docs/FACTOR_LIFECYCLE.md:203-231`

**问题说明**
- 仓库自己的治理标准已经认定当前还不具备可对外发布状态。
- 若现在按“因子库已可交付”对客户报价或收定金，交付口径与仓库内部状态机直接冲突。

**整改标准**
- 在客户材料中改口径为“研究原型/候选因子平台”，停止使用“现货因子库”“可直接交付”表述。
- 至少拿出首批带证书因子白名单，并附完整证书、批准记录、重验机制和摘牌 SLA。

### R3. 交付范围口径严重不一致：文档称 134 因子，代码实际暴露 1058，且 live data 仅 33

**判定**：高风险，阻断交付。

**证据**
- 用户指南、技术文档、交付方案均写明当前版本为 134 因子、阶段 0 雏形：`docs/FACTOR_DB_USER_GUIDE.md:8-15`，`docs/FACTOR_DB_TECH_GUIDE.md:21-24`，`docs/FACTOR_DB_DELIVERY_PLAN.md:23-27`
- 交付方案验收标准写明 `/api/factor-db/factors` 应返回 134 条：`docs/FACTOR_DB_DELIVERY_PLAN.md:118-127`
- 代码实际汇总了 QAPI33、ALPHA101、GTJA191、TDXGS、JQ110、ALPHA158、ALPHA360、BARRA、JQGM，共 1058 条：`research_core/factor_db/metadata.py:3-25`，`research_core/factor_db/metadata.py:415-424`，`research_core/factor_db/metadata.py:483-502`
- 实测 `get_stats()` 返回 `total_factors = 1058`，`factors_with_live_data = 33`

**问题说明**
- 客户无法知道自己买到的是“134 个标准化可交付因子”，还是“1058 个混合来源目录项，其中大量没有因子值、没有统一可交付口径”。
- 这不是单纯文档过期，而是交付范围定义失效。

**整改标准**
- 冻结正式交付清单：逐项列出“已交付可用”“仅元数据”“需外部环境计算”“规划中”四类。
- API 默认返回应与合同清单一致；扩展目录必须显式标记为“非本期交付”。

### R4. 数据服务无客户鉴权且 CORS 全开放，可匿名代理后端持牌数据

**判定**：高风险，阻断交付。

**证据**
- `create_app()` 直接对 `/api/*` 开放 `origins="*"`：`research_core/factor_db/api.py:215-221`
- `/factors/{factor_id}/values` 与 `/export` 没有任何客户鉴权或权限判断：`research_core/factor_db/api.py:142-172`
- 服务层直接用后端环境变量 token 代理 Quant API：`research_core/factor_db/service.py:39-46`，`research_core/data_loader/quant_api_client.py:98-115`
- 技术文档明确写明“鉴权：无（原型）”：`docs/FACTOR_DB_TECH_GUIDE.md:147-155`

**问题说明**
- 只要服务对外暴露，匿名请求就可以借助服务端 token 调持牌因子数据。
- 这会把内部或受限数据源变成无客户隔离的公共代理，属于明显合规与商业授权风险。

**整改标准**
- 增加客户级身份认证、租户隔离、审计日志和访问配额。
- 默认关闭跨域全开放；按正式前端域名白名单放行。
- 将“值查询/导出”分为公开目录与授权数据两个权限面。

### R5. 交付清单承诺的关键文件/路径不存在

**判定**：中风险，影响客户签收。

**证据**
- 交付方案声明以下路径存在，但仓库中实际不存在：
  - `research_core/factor_db/metadata/`：`docs/FACTOR_DB_DELIVERY_PLAN.md:260`
  - `docs/FACTOR_DB_DICTIONARY.md`：`docs/FACTOR_DB_DELIVERY_PLAN.md:261`
  - `docs/FACTOR_DB_TECHNICAL.md`：`docs/FACTOR_DB_DELIVERY_PLAN.md:262`
  - `runtime/factor_db_smoke_test.py`：`docs/FACTOR_DB_TECH_GUIDE.md:49`，`docs/FACTOR_DB_TECH_GUIDE.md:120-127`
- 实测以上路径均不存在。

**问题说明**
- 客户按文档逐项验收时，会直接判定“交付清单不实”或“交付资料不完整”。

**整改标准**
- 二选一：要么补齐实物文件，要么统一修正所有文档、截图、演示话术和验收表述。

### R6. 回归测试与验收命令失效，当前无法形成稳定验收基线

**判定**：中风险，阻断正式验收。

**证据**
- 从仓库根目录直接运行 `pytest -q tests/test_factor_db.py` 失败，报 `ModuleNotFoundError: No module named 'research_core'`
- 使用 `python -m pytest -q tests/test_factor_db.py` 虽能启动，但 4 条用例失败，因为测试仍按旧口径断言 1040/不含 BARRA、JQGM：`tests/test_factor_db.py:21-29`，`tests/test_factor_db.py:41-45`，`tests/test_factor_db.py:74-75`，`tests/test_factor_db.py:81-84`，`tests/test_factor_db.py:113-116`

**问题说明**
- 客户验收最怕“命令写在文档里，但一跑就挂”。
- 当前既没有稳定的标准测试入口，也没有与最新元数据范围同步的断言基线。

**整改标准**
- 统一唯一验收命令并写入 README/用户手册。
- 修复测试环境路径问题，更新断言基线，确保从仓库根目录一键通过。

### R7. 部署文档与实际部署入口不一致，云端启动的并不是 Factor DB 服务

**判定**：中风险，阻断客户部署。

**证据**
- Factor DB 文档要求独立运行 `python -m research_core.factor_db.api --port 8013`：`docs/FACTOR_DB_USER_GUIDE.md:21-30`，`docs/FACTOR_DB_TECH_GUIDE.md:83-96`
- `render.yaml` 实际启动的是 `gunicorn backend.factor_lab_api:app`：`render.yaml:1-12`
- `backend/factor_lab_api.py` 中看不到 `factor_db_bp` 注册，也没有 `/factor-db/` 路由：`backend/factor_lab_api.py:87-110`，且全文仅出现 `factor_db` 字样于离线数据/信任面板相关逻辑

**问题说明**
- 客户按现有云部署配置上线后，未必能得到文档宣称的 Factor DB 服务。
- 这属于典型“本地能跑、部署不可复现”的交付障碍。

**整改标准**
- 明确唯一生产部署形态：独立 Factor DB 服务，或将其正式挂入 `factor_lab_api` 并同步更新部署文件。
- 补一份部署完成后的端到端验收脚本。

### R8. 真实数据与真值证据不可随交付包复核，且次级验证未完成

**判定**：中风险，影响客户付款和信任。

**证据**
- 真实数据证据摘要明确写明验证依据来自仓库外私有 Word 报告：`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:3-10`，`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:25-30`
- 文档明确写明大文件、凭证和本地数据库细节未提交：`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:10`
- 次级验证尚未完成：`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:23`，`docs/FACTOR_LIBRARY_REAL_DATA_EVIDENCE.md:96`

**问题说明**
- 客户无法仅凭交付包独立复核“这套因子值和效果证据是否真实存在、是否可复跑、是否能对账”。
- 证据链不可随包交付，会显著降低客户信任，尤其在定金阶段。

**整改标准**
- 至少交付可审核的脱敏样例、结果摘要、哈希清单、重跑脚本、报告索引和数据口径说明。
- 对不能随包交付的私有报告，要提供可现场核验机制与清单签字页。

## 四、客户首次使用流程评估

**结论**：当前首次使用门槛偏高，且存在“看起来可用，实则仍是原型”的认知落差。

主要表现：
- 文档多处使用“产品雏形/阶段 0/原型”表述，但界面/API 又呈现产品化形态，客户容易误判成熟度：`docs/FACTOR_DB_USER_GUIDE.md:3`，`docs/FACTOR_DB_TECH_GUIDE.md:3`，`docs/FACTOR_DB_DELIVERY_PLAN.md:114-141`
- 客户无法从目录页直接分辨“可查真值”“仅元数据”“需额外计算环境”的边界。
- 部署需要外部 token、外部 Quant API、可能还依赖 SmartData/RQData/Qlib 等，但缺少一页式客户部署前检查单。

## 五、立即整改清单

### P0：交付前必须闭环

1. 冻结正式交付范围，输出《交付清单矩阵》：
   - 因子 ID
   - 是否本期交付
   - 是否有实时数据
   - 是否仅元数据
   - 是否需客户侧额外环境
   - 是否具备证书
2. 形成《法务与授权证据包》：
   - 代码权属
   - 第三方来源清单
   - 商用边界
   - 侵权风险说明
3. 为数据查询/导出接口补客户鉴权、租户隔离、审计日志。
4. 修复测试入口，给出一条客户可执行且稳定通过的验收命令。
5. 修正文档与部署文件，使本地、测试、线上三套入口一致。
6. 在对外材料中删除“已可正式交付/现货因子库”表述，改为与真实状态一致的口径。

### P1：一周内完成

1. 补齐或删除所有不存在的交付文件引用。
2. 发布首版《客户部署手册》与《问题响应机制/SLA》。
3. 为每类因子增加状态标识：`live_data_ready`、`metadata_only`、`needs_external_env`、`not_in_delivery_scope`。
4. 交付可审核的真值样例和报告索引。

## 六、优化建议

1. 建立“交付发布包”目录，而不是让客户直接从研发仓库猜哪些内容可收货。
2. 输出一页式《客户验收总览》：
   - 可用因子数
   - 有数据因子数
   - 有证书因子数
   - 部署要求
   - SLA
   - 责任人
3. 在 API 中加入 `/delivery/manifest` 端点，直接返回本期合同交付范围和状态。
4. 用版本化证书替代散落文档，做到客户可直接对因子逐项验收。

## 七、最终验收建议

当前建议验收结论：**暂缓签收**。

建议对外统一口径：
- 当前可作为“研究平台/原型因子目录”演示；
- 不应作为“客户已可合法合规投入使用的正式因子库”交付；
- 必须待 R1-R4 全部闭环后，才进入客户复验阶段。
