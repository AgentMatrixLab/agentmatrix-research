fix(run): the watchdog never restarted anything, and prove it now does

Two versions of the detection were silently useless, both by counting the detector:

v1  `pgrep -f pool_watchdog.sh` matched the script's own command line, so it
    reported "already running" and never started at all.
v2  `awk -v pat="$MARKER"` put the marker in the awk process's OWN arguments, so
    `index($0, pat)` matched the awk line and the watchdog always concluded a pool
    was running. A `bash -x` trace settled it: `pool_running` returned 1 for a marker
    that matched nothing on the box, so the branch that restarts never ran. In
    production the marker is `run_pool.sh`, so it had been starting, logging
    "watchdog start", and sleeping forever.

That is the failure mode a safety net must not have -- present, plausible, inert.

The marker now travels in the ENVIRONMENT, which `ps -eo args` does not show, and
the scan skips its own pid, anything naming pool_watchdog, and awk processes. Proven
in a sandbox rather than by killing the live pool: with 2 of 5 shards done and no
pool running, the log reads

  pool is down with 2/5 shards done -- restarting with pinned stamp
  restart #1 issued; now running=1 workers=0
  STUB POOL LAUNCHED ... stamp=WDTEST args=5 2

and the detection semantics check out both ways: a marker matching nothing gives 0,
the real production pool gives 1.

Also fixes two things the first live test exposed. The signal trap cleaned up but did
not exit, so the shell ignored SIGTERM and kept looping -- `timeout 60` fired and the
process ran for another ten minutes; an un-stoppable daemon would restart the pool
underneath the final chain run. And stop_and_deliver.sh now stops the watchdog BEFORE
the pool: with a working watchdog, stopping the pool first leaves a gap where it sees
no pool and no chain and starts a new one, which is the memory contention that killed
shards 004/005.
